# AEMS-11 Cross-Module Integration and Security

This document records the implemented AEMS-11 integration boundary. Source
code and the Feature tests remain authoritative; this document describes the
ownership and security contract that those checks enforce.

## Core ownership

AEMS resolves the existing Core services through the Laravel container. It does
not duplicate users, offices, roles, scope rules, document versions, workflow
execution, notifications, runtime configuration, numbering, Activity Log, or
Audit Trail infrastructure. The `AemsIntegrationStatusService` exposes the
resolved providers and the dashboard integration status endpoint is protected
by the existing `aems.engagement.view` permission and `AuditEngagement` policy.

Document downloads continue to use Core `DocumentAccessService` and exact
`document_versions` records. AEMS exports are generated by authenticated
backend endpoints and remain scope filtered.

## IAP to AEMS boundary

IAP remains the owner of approved annual-plan records. AEMS imports a read-only
snapshot and stores its own lineage on `audit_engagements`:

- `iap_plan_engagement_id` and the related plan/risk/universe identifiers;
- the immutable `source_snapshot` captured at import time;
- AEMS planning-package lineage and risk/process-flow references.

The AEMS IAP gateway no longer writes `iap_plan_engagements` during import or
restore. The legacy `aem_engagement_id` column is retained for compatibility,
but its model attribute is a computed projection of the AEMS relationship when
the stored legacy value is null. Existing IAP screens therefore continue to
display a link without allowing AEMS to mutate an approved IAP source row.

Duplicate imports are prevented by the AEMS foreign-key relationship,
transactional import lock, and the PostgreSQL active-source unique index. The
registry also rejects an existing (including archived) source lineage, so the
operator must restore the existing AEMS engagement rather than create a second
aggregate. Approved IAP plans and their risk systems are never edited by AEMS.

The two IAP risk systems intentionally remain separate:

- `iap_risk_assessments`;
- `iap_universe_risk_assessments`.

AEMS preserves the selected source references and snapshot; it does not merge,
rename, or remove either IAP risk system.

## ARMIS resource boundary

`ResourcePlanningGateway` is the only AEMS resource dependency. The configured
provider reports competency/certification claims, availability and leave or
training conflicts, workload/capacity, planned and actual person-days, and
reconciliation/provider status. The explicit modes are:

- `IAP_INTERIM_FALLBACK` (default and safe fallback);
- `ARMIS_SHADOW` (ARMIS is observed while IAP remains active);
- `ARMIS_AUTHORITATIVE` (only after the independent reconciliation and
  authority gate).

Missing or stale ARMIS data cannot silently approve a team assignment. AEMS
team safeguards and completion reconciliation record the active provider,
authority eligibility, and reconciliation result. No automatic provider switch
or approval is performed.

## CMS boundary

Only a finalized AEMS recommendation included in the exact locked issued Final
Report can cross the boundary. `CmsIntakeService` is the authoritative trust
boundary and creates the immutable CMS intake envelope once. The transfer is
idempotent using the recommendation source identity and transfer key; the CMS
case and initial event are created once in the same transaction.

The immutable source envelope now preserves AEMS source lineage, including the
source type, IAP references, and a SHA-256 hash of the AEMS source snapshot.
CMS owns Action Plans, monitoring, validation, dispositions, reopening, and
closure after intake. AEMS remains the source of the finding, recommendation,
report version, and transfer provenance.

## Security and scope controls

- Integration status is authenticated and uses the existing AEMS engagement
  permission and policy.
- Dashboard metrics, work queues, and exports use `AemsAccessService` scope
  filtering. Non-global users do not receive global IAP/CMS counts.
- Separation-of-duties, assignment-role, status, optimistic-lock, and
  immutable-version guards remain in the existing AEMS services.
- Core document confidentiality and protected download checks remain in force.
- Activity Log, Audit Trail, engagement events, and CMS events record the
  cross-module actions and identities.
- AIS is explicitly outside this phase. No AIS provider, table, route, or
  integration is enabled by AEMS-11.

## Verification contract

The focused `AemsCrossModuleIntegrationTest` verifies that an IAP source row is
byte-for-byte unchanged after import, that AEMS owns the resulting lineage,
that integration status is protected and scope-safe, and that AIS remains out
of scope. Existing AEMS registry, IAP, ARMIS adapter, CMS intake, and report
tests continue to protect the surrounding workflows.
